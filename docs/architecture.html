MAAI architecture

Musaed Abdulrahman AI: a personal assistant for one user. An iPhone home-screen web app talks to one Node server on Render, which reads calendar, mail, tasks and news, and uses Claude to think. Nothing is sent, booked or created without a tap.

Three flows

Ask, then approve

  1. You type, speak, or attach a photo.
  2. Server adds today's calendar, mail, tasks and your profile facts, and streams the question to Claude.
  3. Claude may read data with read_* tools, and proposes actions with propose_*.
  4. Each proposal becomes an editable card. Nothing runs until you tap Approve.
  5. Approve runs once, is written to the audit log, and shows the result.

Briefing and alerts

  1. Scheduler wakes every 30 s and checks reminders, meetings, prayers, briefing time.
  2. Due items go out as Web Push to your phone and as banners in the open app.
  3. The briefing is written by Claude only when the data or period changed, otherwise the saved text is reused.
  4. Day load and counts are computed locally, with no AI call.

Photo or PDF to task

  1. Phone shrinks the photo and uploads it raw.
  2. Server checks the file type from its first bytes and holds it in memory.
  3. Claude reads it (Arabic and English), writes a short brief, and prepares a reminder or Asana task card.
  4. The file is released; only its name stays in the chat.

Design rules the code enforces

No action without a tapEvery send, booking, task and fact is a card the owner approves.
Other people's words are dataEmails, messages, titles, news and documents are defused and named as information.
Secrets stay server-sideKeys live in env vars; the profile refuses passwords and ID numbers.
Deny by defaultUnknown paths under /api are refused; public routes are three and each proves itself.
Fail safeFailed saves retry, an unreadable store stops the server, history never keeps a half-finished tool call.
